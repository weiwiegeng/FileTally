# 当本机遇上 NAS：我用 Tauri 2 + Rust 做了一款「本地×远程」一体化文件工作区 —— FileTally 深度拆解

> **关键词**：Tauri 2、Rust、React 19、桌面应用、NAS、SMB、WebDAV、SFTP、文件管理、双栏浏览、传输队列、SQLite 索引、跨端工程实践  
> **适合人群**：桌面端开发者、全栈工程师、NAS 重度用户、对「本地工具产品化」感兴趣的同学  
> **项目定位**：日常本机 + NAS 文件工作区 —— 浏览、搜索、传输、整理、任务进度，一套搞定

---

## 写在前面：为什么要再做一个「文件管理器」？

如果你也经历过下面这些场景，大概能立刻共情：

- Finder / 资源管理器打开 NAS 卡到怀疑人生，搜个文件名像开盲盒；
- 本机一份、群晖一份、再加一台办公机 SFTP，三处文件谁最新全靠感觉；
- 想从 A 共享拷到 B 共享，系统工具不支持「远程↔远程」，只能先下到本机再上传；
- 周末想清理磁盘，却没有一份「可执行」的清理建议，只能肉眼扫文件夹；
- 财务 / 项目交付场景：Excel 名单和实际目录对不上，人工核对到眼花。

市面上不缺「同步盘」「网盘客户端」「专业 FTP 工具」，但它们往往各自只解决一条链路：要么只同步、要么只传输、要么只浏览。**真正缺的是一个把「本机磁盘 + 多协议 NAS」当成同一工作区来用的桌面产品。**

这就是 **FileTally** 诞生的出发点：

> 不是又一个文件列表 UI，而是一套面向「本地 × 远程」日常文件工作流的桌面工作台。

技术选型上，我们选择了当下桌面端最值得认真做的一条路：

| 层 | 技术 | 为什么选它 |
|----|------|-----------|
| 桌面壳 | **Tauri 2** | 体积小、安全性好、系统能力完整，比 Electron 轻一个数量级 |
| UI | **React 19 + Ant Design 6 + Zustand** | 复杂交互与状态可维护，组件生态成熟 |
| 核心 IO | **Rust** | 扫描、传输、协议、索引、哈希 —— 性能与安全必须沉到系统侧 |
| 索引 | **SQLite（rusqlite bundled）** | 本机文件名秒搜，不依赖外部服务 |
| 凭据 | **系统钥匙串（keyring）** | 密码不进配置文件、不进诊断导出 |

下文会从 **产品、设计、工程架构、核心能力深挖、工程化** 五个维度，把 FileTally 讲透。你可以直接当产品说明书读，也可以当一份 Tauri 实战案例拆解。

## 一、产品视角：把「文件工作流」当成一条产品线来设计

### 1.1 一句话定位

**FileTally = 本机磁盘监控 + 双栏本地/NAS 浏览 + 多协议远程 + 智能搜索 + 持久化传输队列 + 整理/同步/回收站 +（可选）Excel 核对与 AI 空间解读。**

菜单按使用频率分了五组，而不是按「技术模块」平铺：

| 分组 | 模块 | 一句话 |
|------|------|--------|
| **日常** | 磁盘监控、文件浏览、远程连接 | 每天都会打开 |
| **查找与传输** | 智能搜索、文件传输、任务中心 | 找得到、传得稳 |
| **整理工具** | 规则筛选、批量整理、轻量同步、回收站 | 让目录「活」起来 |
| **智能工具** | 智能分析 | 空间统计 + 可配置 AI 解读 |
| **专业工具** | 智能检查（Excel） | 名单 ↔ 目录核对 |

这种分组本身就是产品决策：**先服务「每天都在用」的人，再服务「偶尔专业场景」的人。** Excel / AI 明确标注为可选专业能力，避免主路径被复杂功能淹没。

### 1.2 目标用户画像

1. **NAS 家庭 / 工作室用户**  
   群晖、QNAP、TrueNAS，日常照片、工程文件、备份盘。需要稳定的 SMB/WebDAV，以及「本机 ↔ NAS」对照浏览。

2. **开发者 / 运维**  
   多台机器、SFTP 服务器、临时目录同步。需要可取消任务、诊断导出、不瞎存密码。

3. **办公交付场景**  
   用 Excel 管交付清单，目录里要「有这些文件」。智能检查把「名单核对」产品化。

### 1.3 核心产品原则（比功能列表更重要）

| 原则 | 落地表现 |
|------|----------|
| **路径统一** | 本地路径与 `remote://{connectionId}/相对路径` 在 UI 里一视同仁 |
| **长任务可管** | 传输 / 搜索 / 同步 / 整理统一进 JobRunner + 任务中心，可取消、可重试 |
| **先预览再执行** | 批量整理、冲突策略、同步差异对比 —— 先看见再动手 |
| **凭据不出圈** | 密码进系统钥匙串；诊断 JSON 明确不含密码 |
| **本机优先、远程诚实** | 本机可建 SQLite 索引秒搜；NAS 全目录扫描会明确提示代价 |

很多工具会假装「远程和本地一样快」。FileTally 选择诚实：远程搜索就是扫描，UI 会说清楚 —— 这是对用户时间的尊重。

### 1.4 和「传统文件管理器」差在哪？

| 能力 | 系统文件管理器 | 专用 FTP 客户端 | 同步盘 | **FileTally** |
|------|----------------|-----------------|--------|---------------|
| 本机浏览 | ✅ | 弱 | 弱 | ✅ 双栏 + 预览 |
| 多协议 NAS | 挂载依赖系统 | 偏传输 | 自有协议 | ✅ SMB / WebDAV / SFTP |
| 远程↔远程 | 通常不行 | 看产品 | 通常不行 | ✅ 经本机临时目录中转 |
| 持久化传输队列 | 弱 | 部分有 | N/A | ✅ localStorage 可恢复 |
| 规则整理 / 轻量同步 | 无 | 无 | 重同步 | ✅ 可预设、可定时 |
| Excel 名单核对 | 无 | 无 | 无 | ✅ 专业工具 |
| AI 空间解读 | 无 | 无 | 无 | ✅ 可配置 Provider |
| 体量 / 安全模型 | 系统级 | 中等 | 中等 | Tauri 精简壳 + Rust IO |

结论不是「取代 Finder」，而是：**在系统管理器之上，补齐「跨协议工作流 + 可编排任务」这一层。**

## 二、设计视角：一个「工作台」该长什么样

### 2.1 信息架构：侧栏分组 + 跨页导航

主界面是经典的 **左侧导航 + 右侧工作区**，但做了两件对体验很关键的事：

1. **菜单按心智模型分组**（日常 / 查找与传输 / 整理 / 智能 / 专业），降低「功能很多但找不到」的认知负荷。  
2. **跨页面上下文传递**：例如在双栏浏览里选中文件 → 一键跳到「传输」页，自动带上源/目标与方向；从远程连接页可直接把 `remote://` 根目录丢进浏览器某一栏。

这属于 **导航即工作流**：页面不是孤岛，而是流水线上下游。

### 2.2 双栏浏览：对照才是刚需

对 NAS 用户，「左本地、右 NAS」几乎是肌肉记忆（Total Commander / Directory Opus 那一派）。FileTally 的双栏不是装饰：

- 左右各自独立根目录（本地或 `remote://`）；
- 支持跨栏复制 / 移动（远程侧语义会诚实提示，例如部分场景「移动」实质是复制链路）；
- 设置里可开关双栏，单栏用户不被绑架。

设计上刻意避免做成「又一个漂亮卡片墙」：文件工作区的第一视觉锚点应该是 **路径、列表、选中态、进度**，而不是营销式仪表盘。

### 2.3 任务可见性：后台不是黑洞

大目录扫描、传输、同步如果只转圈，用户会焦虑。FileTally 用统一任务中心表达：

- 状态：排队 / 进行中 / 完成 / 失败 / 已取消  
- 类型：搜索、传输、同步、分析、整理、Excel…  
- 操作：取消、重试、清除已完成  

后端 `JobRunner` 分配 job id，前端 `TaskBridge` 监听 Tauri 事件写入 `taskStore` —— **进度是产品功能，不是附属调试信息。**

### 2.4 主题、国际化与「专业但不压抑」

- 主题跟随系统或手动浅/深色（Ant Design `ConfigProvider` + 自定义色板）；  
- 中 / 英完整 i18n（`i18next`），设置项、错误码、任务文案都走翻译表；  
- 预览链路覆盖图片、PDF、文本、音视频、以及 Word / Excel 轻量预览 —— 减少「为了看一眼就另开应用」的摩擦。

设计原则可以浓缩成四句：

1. **自动能做的不要让用户点**（磁盘发现、权限、默认页）；  
2. **层级清晰**（树 + 列表 + 面包屑）；  
3. **懒加载 + 虚拟滚动**（大目录不卡死主线程）；  
4. **危险操作可逆**（回收站、整理可撤销最近一次、冲突策略显式选择）。

## 三、架构视角：Tauri 2 时代的「正确分层」

### 3.1 总览

```
┌─────────────────────────────────────────────────────────────┐
│  React 19 UI（Ant Design 6）                                 │
│  Zustand stores · i18n · localStorage 队列/设置               │
└───────────────────────────┬─────────────────────────────────┘
                            │ invoke / listen（Tauri IPC）
┌───────────────────────────▼─────────────────────────────────┐
│  Tauri 2 Shell                                               │
│  commands/*  ·  JobRunner  ·  RemoteSessionStore  ·  diag    │
└───────────────────────────┬─────────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   本机 FS / 磁盘      SMB·WebDAV·SFTP      SQLite 索引
   walkdir / sysinfo   smb2 / reqwest / ssh2   rusqlite
                           keyring 凭据
```

**边界很清晰：**

| 层 | 职责 | 不做什么 |
|----|------|----------|
| React | 布局、表单、列表/树、任务 UI、客户端持久化 | 不直接碰文件系统协议细节 |
| IPC | 类型化 `invoke('command', payload)` + `emit` 进度 | 不塞业务逻辑 |
| Rust commands | IO、协议、扫描、传输、索引、诊断 | 不管像素级 UI |

这也是为什么 FileTally 能把「远程协议」和「双栏 UX」解耦：前端只认识字符串路径；是否 `remote://` 由 `path_util` 统一解析。

### 3.2 关键抽象：`remote://` 虚拟路径

```text
remote://{connectionId}/relative/path
```

这一小段设计，决定了后面几乎所有功能可以「本地 / 远程同构」：

- 浏览、搜索、传输、整理、Excel 核对 —— 都能吃同一套路径；  
- 解析时拒绝 `..` 穿越；  
- 会话态放在 `RemoteSessionStore`（`Arc` + Tauri `manage`），而不是散落在各 command。

对产品来说，用户感知是：「NAS 也是一个文件夹」。  
对工程来说，这是 **Protocol-agnostic Path Facade** —— 后面加协议，UI 几乎不用改。

### 3.3 状态管理：少而准的 Zustand

没有强行上「巨型 Redux」。实际切分与业务同构：

| Store | 职责 |
|-------|------|
| `settingsStore` | 主题、语言、双栏、传输并发等（persist） |
| `transferStore` | 源/目标、冲突、进度；队列序列化 |
| `dualPaneStore` / `navigationStore` | 双栏根目录、跨页跳转上下文 |
| `taskStore` | 与后端 job id 对齐 |
| `syncPresetsStore` | 轻量同步方案本地保存 |
| `searchStore` / `analysisStore` … | 各域 UI 状态 |

长任务进度走事件总线，而不是轮询 `invoke` —— 在桌面端这是更干净的模型。

### 3.4 JobRunner：把「可取消」做成基础设施

传输、搜索、同步、分析、Excel、规则筛选、整理 —— 全部纳入统一 job 生命周期：

- `begin_job(kind)` → 分配 id  
- 循环中检查 `is_cancelled(job_id)`  
- `end_job` + 诊断环缓冲打点  

没有统一 runner 时，每个模块自己搞取消标志，最后一定会出现「有的任务取消不了、有的取消了 UI 还在转」的体验债。**把取消做成平台能力，是桌面工具成熟度的分水岭。**

### 3.5 诊断导出：为真实世界排错而生

`diag` 模块保留最近约 200 条结构化事件（时间、级别、code、message、job_id），设置页可导出 JSON：

- 含 `app_version`  
- **明确不含密码**  
- 覆盖传输 prepare / cancel / 同步结束等关键节点  

这不是「开发者自嗨日志」，而是产品级售后能力：用户出问题，你能拿到可复现上下文，而不是「我这边好好的啊」。

## 四、核心能力深挖：那些真正拉开差距的细节

### 4.1 文件传输：队列、冲突、限速、远程↔远程

传输模块是 FileTally 的「硬核区」，Rust 侧有完整的冲突模型与进度事件：

- **方向**：上传 / 下载；并支持 **远程→远程**（经本机临时目录中转）  
- **冲突策略**：覆盖 / 重命名 / 跳过；先检查再执行  
- **限速与并发**：带宽软上限 + 顶层并发 1～8 可配  
- **持久化队列**：前端序列化到 localStorage，异常退出后可恢复、可重试  
- **取消可恢复语义**：覆盖前备份，取消时可尽量还原合并现场  

对用户的价值很直接：  
**大文件、弱网、临时关掉窗口 —— 任务还在。**

### 4.2 智能搜索：本机索引 × 远程全扫

| 场景 | 策略 | 用户感知 |
|------|------|----------|
| 本机目录 | SQLite 文件名索引（可构建） | 接近「秒搜」 |
| `remote://` | 全目录扫描 + 进度事件 | 慢但诚实，可取消 |

搜索路径可混合本地与远程；引擎会拆分 localRoots / remoteRoots，避免用错误策略拖垮体验。

内容向搜索还可结合文档解析（如 PDF 文本提取等能力链路），让「找文件」从文件名延伸到内容层 —— 这是普通文件管理器很少愿意做深的部分。

### 4.3 整理工具三件套：规则、批量整理、轻量同步

**规则筛选**  
可视化多条件（名称、扩展名、大小、时间、路径…）AND/OR 组合，适合「把最近 30 天大于 100MB 的视频捞出来」这类日常查询。

**批量整理**  
重命名、按类型归类、删空目录；支持本地与 `remote://` 根（远程走下载→上传→删旧文件的安全链路）；**先预览再应用，可撤销最近一次。**

**轻量同步**  
不是去碰网盘那套重型同步协议，而是：

- 对比：新增 / 变更 / 多余 / 冲突  
- 模式：单向等  
- 冲突策略可配  
- **方案预设 + 定时调度（SyncScheduler）**

对「项目目录 ↔ NAS 备份目录」这种中等规模场景，轻量同步往往比上完整同步盘更可控。

### 4.4 回收站与清理建议

删除不是「直接消失」：回收站保留清单与影子文件树，支持恢复路径。  
智能分析侧可给出空间占用结构与清理建议，并允许配置 AI Provider 做自然语言解读（例如「哪些目录最值得先处理」）—— AI 是增强，不是门槛；未配置时本地统计仍可用。

### 4.5 专业工具：Excel 智能检查

把「Excel 名单里的每一项，目录里是否都有」做成一等公民功能：

- 支持本地与远程目录核对；  
- 大表虚拟滚动；  
- 结果可对照、可导出思路清晰。

这是典型的 **垂直场景产品化**：通用文件管理器不会做，但真实工作流里高频出现。FileTally 没有假装自己是「万能 AI 办公套件」，而是把这一刀切得很准。

### 4.6 安全与路径校验

桌面文件工具必须在「用户可选任意路径」和「拒绝明显危险输入」之间平衡：

- 拒绝空路径、空字节、相对路径中的 `..`；  
- `remote://` 相对段同样禁止穿越；  
- 密码走 keyring；  
- 诊断导出脱敏。

这不是合规表演，而是 **默认安全姿态（Secure by Default）**。

## 五、工程实践：一个能长期演进的桌面仓库长什么样

### 5.1 技术栈一览（可直接抄作业）

**前端**

- React 19 / TypeScript / Vite 7  
- Ant Design 6 / @ant-design/icons  
- Zustand 5（含 persist）  
- i18next + react-i18next  
- react-window（大列表）  
- pdfjs-dist / mammoth / xlsx（预览与专业工具）  
- Vitest 单测  

**后端（Tauri / Rust）**

- tauri 2（tray-icon 等）  
- tokio + rayon（异步与并行）  
- sysinfo / walkdir  
- smb2 / reqwest(WebDAV) / ssh2(SFTP)  
- rusqlite bundled / keyring  
- calamine + rust_xlsxwriter（Excel）  
- sha2（重复文件内容指纹）  
- pdf-extract 等文档能力  

### 5.2 质量门禁

```bash
npx tsc --noEmit          # 前端类型
npm test                  # Vitest
CARGO_TARGET_DIR=target cargo test --manifest-path src-tauri/Cargo.toml --lib
```

CI（GitHub Actions）把上述检查跑在流水线上 —— 对 Tauri 这种「前后端异构」项目，**缺一不可**：只测前端你会漏协议；只测 Rust 你会漏交互状态机。

### 5.3 许可证与协作

项目采用 **LGPL-3.0**：可商用；对本项目本身的修改随程序分发时，需按 LGPL 开源相应改动。`CONTRIBUTING.md` 对构建、PR、密钥与许可证注意事项有清晰约定 —— 这对开源桌面工具很重要：协议栈依赖多，分发时不能「糊弄许可证」。

### 5.4 发布

```bash
npm run tauri:build
./build.sh windows   # 或 macos / all → release/
```

一条命令面向多平台打包，是桌面产品从「能跑」到「能发」的必经之路。

## 六、一次真实工作流走读（帮助你建立心智模型）

假设你是独立开发者，日常这样用：

1. **早上**：打开磁盘监控，外接 SSD 只剩 12%，心里有数。  
2. **浏览**：双栏左侧 `~/Projects`，右侧 `remote://nas-home/work/`。  
3. **改完代码**：跨栏复制构建产物到 NAS；冲突弹窗选择「重命名」。  
4. **传输页**：队列里还有昨晚未完成的大视频上传，继续跑；限速避免占满家庭带宽。  
5. **搜索**：本机索引里秒搜 `invoice`；NAS 侧全扫找去年合同，任务中心可取消。  
6. **同步**：把 `design/` 与 NAS 备份目录做一次差异对比，确认无意外删除后执行单向同步。  
7. **周五**：跑文件夹分析 +（可选）AI 解读，清理建议进回收站而不是直接粉碎。  
8. **交付周**：Excel 智能检查核对「客户清单 vs 交付目录」，缺文件一目了然。

你会发现：FileTally 卖的不是某一个按钮，而是 **把这些步骤串在同一个应用上下文里** —— 少开三个软件、少记两套密码、少一次「文件到底在哪台机器」。

## 七、技术选型背后的判断（给正在做桌面工具的同学）

### 为什么是 Tauri 而不是 Electron？

- **包体与内存**：Rust 侧原生能力 + 系统 WebView，分发更轻。  
- **安全模型**：能力默认收敛，文件系统与对话框走显式 plugin。  
- **性能边界**：扫描百万文件、算哈希、跑协议 —— 这些本就不该在 JS 里硬刚。

Electron 依然适合强 Web 生态绑定的产品；但 **以 IO 与系统集成为中心的工具**，Tauri 2 已经非常能打。

### 为什么 UI 仍用 React？

Rust 很强，但复杂桌面交互（双栏、冲突模态、任务表、表单校验、i18n）用 React + Ant Design 迭代更快。FileTally 的策略是：

> **把「对」放在 Rust，把「好看且好改」放在 React。**

这是务实的双栈分工，而不是意识形态站队。

### 为什么要自己做 `remote://` 而不是全靠系统挂载？

系统挂载受权限、平台差异、用户是否已挂载影响巨大；应用内会话可以：

- 统一 UX；  
- 统一错误码；  
- 统一传输队列与取消；  
- 在 WebDAV / SFTP 场景不依赖 OS 挂载能力。

当然，系统挂载仍是有价值的补充；但 **产品主路径不应绑架在挂载成功与否上**。

## 十、写在最后：桌面工具的「产品化」到底在优化什么

回顾 FileTally，我认为它真正想回答的不是「能不能列出文件」，而是三句更难的话：

1. **本地和远程能否共用同一套心智模型？** —— `remote://` + 双栏给出了答案。  
2. **长耗时操作能否像现代 App 一样可观测、可取消、可恢复？** —— JobRunner + 任务中心 + 持久化队列。  
3. **专业场景能否不污染日常主路径？** —— 菜单分组与「专业工具」分层。

如果用更「高大上」一点的表述：

> FileTally 是一次把 **异构存储统一访问层（Unified Access Layer）**、**可编排文件任务运行时（Job Runtime）** 与 **以人为中心的工作台 UX** 装进同一个 Tauri 进程的实践。

对开发者，它是一份可参考的 Tauri 2 + Rust IO 全栈样本；  
对用户，它是少折腾一点的本机 × NAS 日常工作区；  
对做产品的人，它提醒我们：**工具类软件的护城河，往往不在炫技功能，而在工作流是否闭环、失败是否可恢复、远程是否诚实。**
